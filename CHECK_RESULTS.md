# Перевірка Forbes Email Studio 0.2.1

Дата: 15 жовтня 2026 року. Базовий коміт GitHub: `6d60619aec155896ce020d13a30e567403b83910`.

## Що перевірено

- Код GitHub звірено з локальним проєктом. Обидва попередні виправлення вже були в репозиторії. Виявлено дві додаткові локальні зміни: повідомлення про права API та тести; їх включено в цей пакет.
- GitHub показує успішний статус Vercel для базового коміту. Адреса з метаданих репозиторію: https://forbes-email-studio.vercel.app . Також увімкнено GitHub Pages — це окрема статична публікація, яка не запускає API Next.js.
- Живий сайт відкриває сторінку входу. Анонімні запити до `/api/studio`, `/api/remote-templates`, `/api/segments` повернули 401 та `Cache-Control: no-store`.
- Перевірено шлях редактор → POST збереження → eSputnik → Blob → GET списку, а також відкриття чернетки, тест, підтвердження, запуск, планування, імпорт і статистику.
- Збережено умовні записи з ETag і читання `useCache: false`. Блокування повторної відправки та прив’язка історії до API-ключа залишаються чинними.

## Виявлені дефекти та зміни

1. Усі помилки запису Blob приховувалися під однаковим повідомленням і повторювалися до шести разів. Тепер є окремі безпечні коди для доступу, середовища, лімітів, недоступності, відсутньої версії та конфлікту. Повторюється тільки підтверджений конфлікт.
2. Запис Blob міг бути успішним при втраченій відповіді. Тепер у службовому файлі є обмежений список ID записів: повторне читання підтверджує результат без дублювання змін.
3. Після створення листа в eSputnik міг не зберегтися службовий запис. Тепер повідомлення містить ID; лист доступний для перегляду. Відновлення дозволене лише для відповідної незавершеної операції CREATE після перевірки тегу, підпису, HTML і налаштувань. Статуси запусків відновлення не скидає.
4. Збій оновлення списку після успішного POST виглядав як помилка збереження. Редактор тепер зберігає отриманий ID та показує окреме повідомлення. Для частково створеного листа навігація не запускає повторний CREATE.
5. Додано перевірку підключень у налаштуваннях. Вона показує версію, коміт, домен і результати API/Blob. Для перевірки Blob використовується окремий тимчасовий файл, а не файл історії. Перевірка не створює і не відправляє листів.
6. Серверні помилки мають безпечні структуровані логи та ID запиту. Сирі відповіді SDK, ключі, заголовки авторизації й тексти листів не журналюються.

## Результати перевірок

- `npm test` — PASS: API, авторизація, CSRF, чернетки, повтори, відновлення, зміни версій, шаблони, імпорт, тест/запуск/планування, статистика, приховування секретів.
- Тести встановленого `@vercel/blob` 2.8.1 — PASS: справжні SDK та OIDC resolver, HTTP-серіалізація, ETag у лапках, конфлікт, втрачене підтвердження, відмова доступу, відсутній ETag, окремий перевірочний запис і його видалення. Лише HTTP-сервіси підставні.
- `npm run build` — PASS: Next.js production та TypeScript.
- `npm run test:runtime` — PASS: справжній production-сервер, HTTP-вхід, авторизоване відображення, захищені маршрути, CSRF, версія відповіді, діагностика відсутніх налаштувань.

## Межі перевірки

Немає авторизованого доступу до змінних середовища вашого Vercel або до приватного сховища та кабінету eSputnik. Точна причина нинішнього живого збою Blob ще не підтверджена. Її покаже перевірка підключень на вашому deployment після встановлення цього пакета. Реальні листи під час перевірки не надсилалися; дані користувача не змінювалися.

Візуальний тест у Chromium не виконано: у середовищі відсутній браузер, завантаження його пакета завершилося помилкою. Інтерфейс перевірено компіляцією TypeScript та відображенням production HTML; взаємодія у справжньому браузері потребує перевірки після оновлення.

Порожня вкладка Vercel Logs не є доказом причини збою. Оновлення дає діагностику на самому сайті та додає журналювання серверних помилок.

## Встановлення пакета

1. Розпакувати ZIP. Усередині — лише нові та змінені файли зі збереженими шляхами.
2. Відкрити корінь репозиторію GitHub → Add file → Upload files.
3. Перетягнути папки `app`, `components`, `lib`, `tests` та файли `package.json`, `package-lock.json`, `README.md`, `CHECK_RESULTS.md` разом. Не завантажувати сам ZIP або зовнішню папку навколо цих файлів.
4. Commit changes у main. Дочекатися нового deployment Ready.
5. Відкрити сайт → Налаштування → Перевірити підключення. Звірити версію 0.2.1 і середовище production.
6. За успішної перевірки відкрити потрібну кампанію. Якщо для незавершеного створення доступне «Відновити чернетку», це відновлює службовий запис того самого листа.

Не змінювати ID робочого простору або видаляти історію для обходу перевірок.
