# Forbes Email Studio 0.2.8 — системна відписка та тест через збережений лист

## Проблема

Тест блокувався через порожні глобальні поля реквізитів і URL відписки. Ручний фіксований URL не відповідає механізму персональних посилань eSputnik. На наданому скриншоті звичного футера є контакт support@forbes.ua та блок керування підписками/відписки; фізичної адреси на ньому не видно.

## Зміни

- Прибрано обов'язковість окремих реквізитів і ручного URL відписки. У налаштуваннях залишається необов'язковий додатковий текст для вбудованих шаблонів. Поле ручного URL замінено поясненням системної відписки та необхідності перевірити доставлений тест.
- Імпортований шаблон зберігає власний футер. Студія не додає до нього ще один глобальний футер. Системні посилання розпізнаються також за текстом усередині вкладених елементів і зберігаються без UTM-переписування.
- Нові вбудовані шаблони не генерують фіктивне посилання відписки з href="#" або персональний URL із застарілого налаштування. Старий неробочий якір з точним текстом «Відписатися від розсилки» та href="#" видаляється; наявні справжні посилання шаблону зберігаються.
- Для тесту створюється окреме збережене повідомлення eSputnik з позначкою [ТЕСТ], правильним відправником, актуальним HTML і без службового коментаря редактора. Чернетка залишається незмінною. Тестові копії мають окремий тег і не потрапляють до каталогу кампаній студії.
- Надсилання використовує POST /message/{id}/smartsend з одним recipients.locator — адресою з налаштувань тестової пошти. База контактів у цьому запиті не передається.
- Успіх вимагає явного status=OK для єдиного відповідного отримувача. Підтримуються results як масив і як одиночний об'єкт. Порожня, помилкова, множинна або невідповідна відповідь не вважається успіхом.
- Службова історія зберігає ID тестової копії та безпечний requestId провайдера. Після втрати відповіді або непідтвердженого результату автоматичного повтору немає. Повторне натискання після підтвердженого тесту тієї самої версії не створює ще одну копію й не відправляє ще один лист.
- Хеш перевіреної версії тепер включає сформований HTML і спосіб тестування. Старий тест попереднього механізму не дозволяє запуск нової версії.

Поля застарілого URL в типах/налаштуваннях залишено для сумісності з наявними підписаними даними. Нове надсилання не вимагає вводити цей URL. Нових змінних середовища чи залежностей немає.

## Джерела

- eSputnik Unsubscribe Forms: система формує персональні посилання та додає блок відписки. Для API рекомендується надсилання збереженого листа: https://docs.esputnik.com/docs/unsubscribe-forms
- Формат запиту та відповіді Send Prepared Message: https://docs.esputnik.com/docs/using-the-send-prepared-message-api-method
- Одиночний об'єкт results також наведено в FAQ API: https://docs.esputnik.com/docs/faq-integrating-with-api

Підготовка листа й передавання в чергу не є доказом доставки або роботи конкретного посилання у вашому акаунті. Це потрібно перевірити на отриманому тестовому листі. Скриншот футера не містить HTML-атрибутів посилань, тому їхній фактичний системний тип із цього скриншота не визначено.

## Встановлення й перевірка

1. Розпакувати ZIP. Завантажити всі внутрішні файли й папки в корінь GitHub-репозиторію зі збереженням шляхів → Commit changes.
2. Дочекатися production Vercel Ready. Відкрити сайт у новій вкладці, перевірити версію 0.2.8.
3. У налаштуваннях перевірити відправника й тестову пошту. Додатковий текст футера можна залишити порожнім. Натиснути «Зберегти налаштування».
4. Відкрити поточну чернетку → «Аудиторія та час» → «Надіслати тест собі».
5. Перевірити отримання листа, тему з [ТЕСТ], прехедер, текст, кнопку та наявність системного блоку відписки. Надіслати результат у чат. Непідтверджене надсилання не повторювати — перевірити журнал і кабінет eSputnik.

У кабінеті eSputnik з'явиться позначена тестова копія. Це окреме повідомлення для перевірки; робоча чернетка зберігає свій ID.

## Перевірки

PASS: npm test; npm run build; production HTTP tests/verify-runtime.mjs --storage, --transformed, --test-ambiguous; DOM tests/verify-navigation.mjs з окремим jsdom 26.1.0.

Перевірено порожні ручні налаштування футера; збереження контактного й системних посилань без UTM; відсутність фіктивного URL; створення окремої копії без метаданих редактора; незмінність оригіналу; рівно одного отримувача; явний результат API в обох форматах; повторні натискання; тайм-аут створення копії до виклику надсилання; втрату підтвердження після прийняття; відсутність повтору; збереження прехедера та історії. Попередні CAS, CSRF, тест/підтвердження/запуск і відновлення залишаються перевіреними.

Тести використовували ізольовані підставні сервіси й вигадані ключі. Реальні листи з цього середовища не надсилалися. Відображення в Chromium і доставку в акаунті користувача не перевірено.
