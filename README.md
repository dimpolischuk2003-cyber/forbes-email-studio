# Forbes Email Studio — MVP без AI та Supabase

Це готовий код окремої студії для GitHub і Vercel. Цей архів не публікує сайт автоматично та не змінює попередній сайт ChatGPT.

Маркетолог обирає дизайн або чинний лист eSputnik, редагує текст, розмір шрифту, фото й кнопки, обирає сегмент або імпортує свою базу, надсилає тест собі та підтверджує відправку або планування.

## Де що зберігається

| Сервіс | Роль |
| --- | --- |
| GitHub | Код студії |
| Vercel | Сайт, серверні запити та налаштування доступу |
| eSputnik | HTML листів, чернетки, шаблони, контакти, відправки та звіти |
| Приватний Vercel Blob | Невеликий службовий файл: ID листів, версії, статуси, підтвердження тестів, ID розсилок та імпортів, останні 200 дій і числові показники звітів |

Supabase, PostgreSQL, Google Таблиця й AI не потрібні. У Blob немає HTML листів, тексту блоків, списків отримувачів чи API-ключа. Blob потрібен для захисту від подвійного запуску між різними серверними процесами Vercel. Це окреме налаштування всередині Vercel; плата залежить від тарифу й використання Vercel. Цей архів не гарантує безкоштовного хостингу. Відправки оплачуються за вашим тарифом eSputnik.

## Запуск покроково

### 1. Завантажте код у GitHub

1. Розпакуйте ZIP.
2. Створіть приватний репозиторій GitHub.
3. Завантажте **вміст** папки `forbes-email-studio-vercel` у репозиторій.
4. Перевірте: `package.json`, `package-lock.json`, `app`, `components`, `lib`, `tests`, `README.md` мають бути у корені репозиторію.
5. Не завантажуйте `node_modules`, `.next` або файли з реальними паролями та ключами. `.env.example` містить тільки приклади.

Якщо вже завантажили попередній архів: замініть його код цим, видаліть стару папку `supabase` та старі тести. Не залишайте старі файли паралельно. Нова версія використовує `tests/verify-v2.mjs`.

### 2. Підключіть репозиторій до Vercel

У Vercel: **Add New → Project → Import Git Repository**. Оберіть репозиторій. Framework: **Next.js**, Root Directory: корінь з `package.json`. Node.js: 22 або 24. Якщо GitHub містить зовнішню папку замість її вмісту, вкажіть цю папку як Root Directory.

### 3. Додайте налаштування

У Vercel → Project → Settings → Environment Variables додайте для **Production**:

| Назва | Що вписати |
| --- | --- |
| `STUDIO_EMAIL` | Ваша робоча пошта для входу |
| `STUDIO_PASSWORD` | Новий окремий пароль від 14 символів для цієї студії |
| `STUDIO_SESSION_SECRET` | Випадковий секрет із 64 шістнадцяткових символів; команда нижче |
| `ESPUTNIK_API_KEY` | Окремий API-ключ цього кабінету eSputnik з правами на листи, шаблони, групи, імпорт контактів та розсилки |
| `EMAIL_SENDER_EMAIL` | Вже підтверджена адреса відправника в eSputnik |
| `ESPUTNIK_SEND_ENABLED` | Спочатку `false`: тест собі працює, масовий запуск заблокований |

Секрет можна згенерувати на комп’ютері з Node.js:

```bash
npm run key:generate
```

Збережіть отримане значення як `STUDIO_SESSION_SECRET`; команда нічого не записує у файл. Не міняйте його при кожному публікуванні: він підписує сесії та дані редактора у чернетках.

Опційно додайте `STUDIO_NAME`, `EMAIL_SENDER_NAME`, `EMAIL_FOOTER_ADDRESS`, `EMAIL_UNSUBSCRIBE_URL`, `ESPUTNIK_TIMEZONE`, `ESPUTNIK_TIMEZONE_CONFIRMED`, `EMAIL_SUBSCRIPTION_KEYS`. Це спільні початкові налаштування команди. Повний перелік є у `.env.example`.

Для окремих входів колег використайте `STUDIO_USERS_JSON` за прикладом у `.env.example`. Кожен матиме власну пошту/пароль; листи та бази спільні, дії фіксуються під поштою користувача. Тут немає окремих ролей адміністратора/маркетолога, MFA або функції «забув пароль»: адміністратор змінює пароль у Vercel. Зміна пароля завершує старі сесії. Локальне обмеження спроб входу не є глобальним між серверами; правила Firewall Vercel можна налаштувати для `/api/auth/login`.

### 4. Підключіть приватний Blob у Vercel

У цьому ж проєкті відкрийте **Storage → Create Storage → Blob**. Оберіть **Private**, задайте назву та підключіть сховище до **Production** цього проєкту. Vercel додає потрібні серверні реквізити автоматично.

Код підтримує `BLOB_READ_WRITE_TOKEN` або підключення через `BLOB_STORE_ID` і автоматичний OIDC із контексту запиту Vercel. Ручне копіювання `VERCEL_OIDC_TOKEN` не потрібне. Не створюйте публічний Blob. Без сховища студія блокує збереження і запуск: статус відправки має переживати перезапуск сервера.

Якщо проєкт уже розгорнули, після додавання сховища і змінних зробіть **Redeploy**.

### 5. Увійдіть і заповніть відправника

Відкрийте адресу Vercel та увійдіть із поштою й паролем із кроку 3. У «Налаштуваннях»:

1. Перевірте ім’я та підтверджену адресу відправника.
2. Вкажіть власну тестову пошту.
3. Додайте реквізити компанії й чинне HTTPS-посилання відписки з HTML ваших листів eSputnik.
4. Звірте часовий пояс із кабінетом eSputnik та поставте відповідну позначку.
5. Натисніть «Зберегти налаштування».

Налаштування, введені у студії, діють для цього користувача в цьому браузері. Для спільних значень на всіх комп’ютерах адміністратор використовує змінні Vercel із кроку 3.

### 6. Перевірте один лист без масового запуску

1. Оберіть дизайн або знайдіть свій шаблон у eSputnik.
2. Відредагуйте лист. Для фото використайте публічне HTTPS-посилання з галереї eSputnik або вашого сайту; завантаження фото з комп’ютера ця версія не має.
3. Натисніть «Зберегти чернетку».
4. У кабінеті eSputnik перевірте, що лист із цією назвою з’явився у списку повідомлень.
5. У студії перейдіть до «Аудиторія та час» → «Надіслати тест собі».
6. Перевірте лист у пошті: текст, фото, кнопки, UTM та відписку.
7. Закрийте й знову відкрийте студію та чернетку — контент має відновитися.

Чинний шаблон eSputnik лишається оригіналом. Його вибір завантажує копію у редактор; збереження створює новий лист. «Зберегти як шаблон» створює шаблон у eSputnik.

### 7. Дозвольте запуск

Після перевірки змініть `ESPUTNIK_SEND_ENABLED` у Vercel на `true`, зробіть **Redeploy** та перевірте позначку «Дозволити запуск розсилок» у студії. Зміна налаштувань вимагає нового тесту перед запуском.

Оберіть базу, надішліть тест, натисніть «Перевірити запуск», звірте кількість контактів, тему й час, підтвердьте запуск. При плануванні час передається до eSputnik — студія не потребує Cron і не має бути відкритою в браузері.

Першу реальну відправку зробіть на невеликий внутрішній сегмент.

## Як працює редактор і збереження

- Чернетка — повідомлення eSputnik з тегом `forbes-email-studio-v2`. Шаблон має також `template: true`.
- У HTML чернетки є підписаний службовий коментар зі станом редактора. Він дозволяє відновити блоки, тему, аудиторію та планування.
- При запуску створюється окреме фінальне повідомлення **без цього коментаря**, потім розсилка. Чернетка лишається для перегляду та копіювання.
- Фото й кнопки можна вставляти та переміщувати між блоками; текст форматувати й змінювати його розмір. Для імпортованих листів доступний редактор HTML-макета з попереднім переглядом.
- Зовнішні зміни HTML у кабінеті eSputnik скидають підтвердження тесту. Якщо службовий коментар прибрали або HTML нормалізувався, лист відкривається як імпортований HTML, без втрати самого контенту.
- API eSputnik не надає використаного тут атомарного порівняння версій для PUT. Не редагуйте один лист одночасно у студії та кабінеті eSputnik: перевірка змін зменшує ризик, але не замінює блокування з боку eSputnik.
- Чернетки з відсутнім службовим статусом не можна запускати; їх можна завантажити як джерело копії через розділ шаблонів після перевірки у кабінеті.

## Імпорт і звіти

CSV/XLSX читаються у браузері: виберіть аркуш і колонку email. Студія показує помилки та прибирає повтори, потім передає контакти у eSputnik. Ліміт MVP — 15 000 адрес за імпорт, до 3000 за запит; сервер також обмежує розмір запиту. Список адрес у студії не зберігається. Поки готовність імпорту не підтверджено, використання цієї бази для запуску блокується.

Статистика запитується з eSputnik за ID розсилки. Показники відображаються тільки якщо API їх повернув. Якщо числових показників немає, є імпорт CSV-звіту eSputnik; автоматичну доступність усіх метрик потрібно перевірити на вашому кабінеті. API-адаптер не підставляє розмір бази замість доставок і не вигадує результати.

Для читання повідомлень eSputnik діють обмеження API вашого кабінету. MVP завантажує контент лише при відкритті/збереженні/перевірці, а не всіх листів одразу. Для великої команди може знадобитися збільшення API-ліміту.

## Якщо статус «Потребує перевірки»

Це означає, що відповідь сервісу або збереження статусу не підтверджено. Відправка **могла відбутися**. Перевірте журнал та кабінет eSputnik за ID/назвою листа, розсилки або тегом операції. Автоматичного повтору запуску немає. Не створюйте копію для повторного масового запуску, поки не перевірили попередню дію.

Не видаляйте службовий Blob і не змінюйте `STUDIO_WORKSPACE_ID` для «скидання» помилки. API-ключ прив’язаний до збереженої історії: після його заміни операції блокуються, доки адміністратор не перевірить той самий кабінет і не перенесе прив’язку. Це запобігає повторному запуску старих кампаній або змішуванню історії різних кабінетів.

## Оновлення 0.2.1 і перевірка підключень

Після завантаження цього пакета у GitHub дочекайтеся нового deployment Vercel зі статусом Ready. Адреса проєкту: https://forbes-email-studio.vercel.app . GitHub Pages не виконує серверні API цього застосунку.

У студії відкрийте **Налаштування → Перевірити підключення**. На екрані з'являться версія 0.2.1, короткий SHA коміту, середовище та домен. Перевіряються читання листів і груп eSputnik, наявність відправника, створення/читання/оновлення окремого перевірочного Blob та відхилення застарілої версії. Тимчасовий запис видаляється. Перевірка не змінює листи, бази або службовий файл кампаній і не надсилає листів.

Ця перевірка доступна після входу, вимагає POST з того самого origin та не показує API-ключі, паролі або OIDC-токени. На екрані видно конкретний код помилки, якщо доступ відхилено, сховище призупинене, не дозволене середовище, відсутній ETag, є конфлікт або втрачено підтвердження. Наявність змінної середовища сама по собі не вважається перевіркою працездатності.

У разі втрати відповіді Blob програма повторно читає маркер конкретного запису. Якщо він уже збережений, функція повертає початковий результат без повторного застосування змін. Повтори з паузою застосовуються тільки для підтверджених конфліктів версій. Інші помилки повертаються одразу після перевірки факту запису. Невідомі результати відправки, тесту або імпорту автоматично не повторюються.

Якщо лист створений у eSputnik, але його службовий запис не підтверджено, повідомлення містить ID листа. Він відкривається для перегляду зі статусом «Потребує перевірки». Кнопка **Відновити чернетку** з'являється лише за наявності відповідної незавершеної операції CREATE. Сервер додатково звіряє тег операції, підписаний стан редактора, HTML, назву, тему, налаштування та відсутність чинного запису. Відновлюється статус тієї ж чернетки; новий лист не створюється. Статуси тестів і запусків ця дія не скидає. Якщо перевірки не пройдені, відновлення блокується.

Успішний POST збереження більше не перетворюється на помилку через подальше оновлення списку. У такому разі редактор показує окреме повідомлення та зберігає отриманий ID.

У Vercel Logs серверні помилки записуються як `studio.storage` і `studio.request`. У записах є код, операція й ID запиту без сирих відповідей SDK, ключів, заголовків авторизації або тексту листа. Порожній екран Logs може залежати від доступу, контексту проєкту та фільтрів; він не використовується як доказ справності сховища.

**Межа перевірки пакета:** код і SDK перевірено локально з контрольованими відповідями сервісів. Доступ до реальних змінних Vercel і кабінету eSputnik автора пакета відсутній. Остаточну роботу підключення підтверджує перевірка на вашому deployment і тестовий лист на власну адресу.

## Локальна розробка і перевірка

```bash
npm ci
cp .env.example .env.local
# Заповніть .env.local своїми серверними реквізитами, не комітьте його.
npm run dev
```

```bash
npm test
npm run build
npm run test:runtime
```

Тести використовують підставні eSputnik і Blob, окремі серверні збірки та справжню логіку авторизації/запитів/атомарного збереження. Перевіряються збереження/відновлення чернеток, шаблони, паралельні запуски, зміни версій, невизначені відповіді, імпорт, планування, статистика, приховування ключів та зміна облікових даних.

Збірку і ці тести перевірено. Реальну відправку з вашим API-ключем, обробку HTML вашим кабінетом, права імпорту й доступність метрик потрібно пройти за кроками 6–7; у цьому архіві немає ваших ключів.
